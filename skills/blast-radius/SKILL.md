# 影響範圍

找出改動在別處會弄壞什麼，趁它還沒上線。用於 "blast radius of X"、"what could this break"，或審查一個你還不信的小 diff。

與 `how-code-work` 和 `why-code-work` 配套。`how-code-work` 講程式碼做了什麼，`why-code-work` 講它為什麼長成那樣，影響範圍講它在別處會弄壞什麼。

列出呼叫方不是這份工作。代理一秒就能 grep 出來。這份工作要找的是 grep 看不出的破壞。

## 不要相信你自己寫的報告

一份聽起來對的影響範圍報告一文不值。無論真假，讀起來都很有說服力。所以不要只把報告交回去。找出整件事所依賴的一兩個事實，然後跑程式碼把它們證明出來。

### 你有多確定

對改動安全所依賴的每一個事實，只要代價不高，就儘量往這個列表下面推，並說明停在了哪一步。

1. 你只是這麼說了。單憑這條毫無價值。
2. 你指到了那一行。真實的 `file:line`，或庫自己的原始碼。
3. 你證明了壞情況不會發生。你一步步走完失敗路徑，發現它到不了。
4. 你跑過了。一個指令碼或測試，呼叫真實程式碼，你錯了就大聲報錯。
5. 你在執行中的應用裡復現了它。

第 4 步通常就是一個小指令碼：匯入應用打包的同一個庫，呼叫你擔心的那個函式。

## 步驟

1. 讀懂改動。diff，它新增、修改、刪除的符號，以及它現在有哪些行為不同了，包括 diff 沒明說的那部分。用 `why-code-work` 的第 2 步把 PR 和提交拉出來（`~/.agents/skills/why-code-work/SKILL.md`，那一步叫「立住程式碼錨點」）。
2. 找出它之所以安全的那個事實。多數看起來有風險的改動，是因為單一事實才安全的，比如「這個呼叫只丟棄已經失效的快取條目，別的什麼都不做」。找到那個事實。只要它成立，大部分有風險的情況一下子就被排除。時間花在這裡，別花在一長串說不準的事上。
3. 看 grep 停在哪。讀你呼叫的庫的原始碼，核對它鎖定的版本和任何本地補丁。搞清楚東西在什麼時候執行：microtask、解除安裝與 teardown、Solid 還是 React。追蹤符號搜尋漏掉的：API 返回的 JSON、資料庫的某一列、wire format、讀同一批位元組的另一種語言、一個功能開關、往下三層之外的程式碼。
4. 對每個風險說實話。給出它真正發生的可能性和發生後的真實代價。保留你已確認的風險。把你查過並排除的另列一份。規則和 `why-code-work` 一樣（`~/.agents/skills/why-code-work/references/epistemics.md` 的置信度分層）。引用真實的 `file:line`，搜不到也是一個答案，絕不要編造呼叫方或 API。
5. 證明那個事實。寫一個指令碼或測試跑真實程式碼，執行它，把結果貼出來。放哪：repo 有現成驗證慣例就照它（既有的測試目錄、`bun test`、`pytest`、`scripts/`）；沒有就放 `$TMPDIR`，跑完可丟。放 repo 裡的要能重跑。

## 要交回什麼

- **它做了什麼。** 改了什麼，包括不明顯的部分。
- **它之所以安全的那個事實。** 陳述它，說明你推到了哪一步，並給出證明。如果證明不了，就寫 unproven。
- **風險。** 每條寫明它怎麼壞、`file:line`、可能性多大、多嚴重，以及怎麼查。把要緊的那些的證明貼出來。
- **已排除。** 你查了什麼、為什麼沒問題。
- **合併之前。** 能抓到真實 bug 的最省事的測試或復現，包括你寫的那個指令碼。

寫的時候套用 **unslop** 的規則（`~/.agents/skills/unslop/SKILL.md`；它是使用者顯式觸發的 skill，直接讀檔套用）。引用真實程式碼，在發到任何公開的地方之前剝掉任何私密內容。

**回覆：** 上面那份報告，其中那個安全事實要麼已被證明，要麼標為 unproven。
