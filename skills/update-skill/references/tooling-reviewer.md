## 視角補充：代理自己去取上下文

標出每一次：使用者手動遞了上下文，而代理本來可以用 MCP 工具自己取到（工單系統、聊天、文件、可觀測性、錯誤跟蹤、原始碼管理、分析數倉、CI、設計工具等），或用另一個 skill 取到。每一次都寫：

- Principle: 一句話，說明代理本該自動去查什麼。
- Evidence: 使用者的手動交接（例如工單 ID、討論串 URL、可觀測性 trace ID、錯誤跟蹤事件連結、"this is from PR #X"（這來自 PR #X）、設計工具 URL）。
- Routing: 擁有這條工作流的 skill。擴充套件它，讓它去調相關的 MCP 工具或同級 skill，這樣下一個代理會自己把上下文取來。

這種模式的例子：

- 使用者貼了工單標題，因為代理沒去查工單 MCP。Routing: 相關的分診 skill 應該先呼叫工單 MCP。
- 使用者描述了一個 flaky 測試，代理本來可以用可觀測性 MCP 查到。Routing: 除錯 skill 應該提到可觀測性 MCP。
- 使用者丟來一條討論串連結，代理本來可以用聊天 MCP 取到。Routing: 相關 skill 應該提到聊天 MCP。

到 <ABSOLUTE_PATH> 讀取當前對話記錄（沒給路徑就用下面的摘要）。

掃描這些：

- 代理不得不自己摸出來的工具呼叫和命令 flag
- 庫或框架的怪癖（配置、lockfile、環境變數的行為、某個版本才有的坑）
- 看一眼程式碼看不出來的檔案或路徑約定
- 測試命令、CI flag，以及怎樣在本地復現一次失敗的執行
- 除錯入口：怎樣抓一條 trace、日誌落在哪、打哪個 RPC
- 構建、包管理器、沙箱上的意外，第一次會多耗掉好幾分鐘的那種

## 範圍只限這次會話真正用過的 skill 和工具

發現只路由到這份對話記錄用過的 skill、工具或 MCP。下面任一情況出現，就算這個 skill 用過了：對話記錄裡有一次 `read` 或 `skill` 呼叫，讀的是它的 `SKILL.md`（在 `~/.agents/skills/` 或專案 `.opencode/skills/` 下）；某次 `subagent` 提示詞寫了它的路徑；或者某次工具呼叫（`shell`、`grep`、MCP 等）對得上它文件裡的命令。父代理沒開啟過的 skill，推測性路由不算。

兩種發現形態有效：

- 父代理呼叫了這個 skill，你在它正文裡發現了真實缺口。路由到該 skill 的相關章節。
- skill 在目錄裡看得到，但在本該幫忙時沒有觸發。改它的 description，讓以後的代理能選中它。路由寫成 `tune description: <skill path>`。

沒呼叫過、也不是漏觸發候選的 skill，丟掉。

每條可複用的經驗都列出來。每條包含：

- Principle: 一句話，點明這條約定或技術事實。要具體到以後的代理能認出什麼時候用得上。
- Evidence: 對話記錄裡的確切時刻（輪次或一小段原文，帶上命令或 flag）。
- Routing: 最相關的現成 skill（對話記錄裡出現的那個 `SKILL.md` 路徑），或者該觸發卻沒觸發時寫 `tune description: <skill path>`，或者寫 "new skill: <kebab-name>"。

跳過瑣碎的（錯別字、重試），也跳過父代理已經照著做的 skill 裡顯而易見的內容。跳過會隨程式碼變化而過時的實現細節：具體 SHA、當前檔案路徑、版本號、精確位元組數。約定能推廣到別處。釘死的細節不行。
