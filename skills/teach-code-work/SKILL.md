# Teach

**你要在一段平實的講述裡、按對方的節奏，講清一樣東西是什麼、怎麼運作、為什麼這樣設計。目標是讓他弄懂，而不是去改動任何東西。**

Teach 建立在 `how-code-work` 和 `why-code-work` 之上。先搞清楚這項工作是做什麼的、牽涉到哪些東西，然後跑 `how-code-work` 瞭解它怎麼運作，跑 `why-code-work` 瞭解它為什麼是這樣。

這兩個 skill 都設了 `disable-model-invocation`，模型叫不動。所以自己讀檔，照它們的流程跑：

- `~/.agents/skills/how-code-work/SKILL.md`
- `~/.agents/skills/why-code-work/SKILL.md`

兩份都讀全文。要派子代理時，照那兩份檔案裡「派生子代理」一節的規定走（`subagent`、不指定 `model`、提示詞寫明只讀）。`how-code-work` 和 `why-code-work` 需要的子代理放在同一則訊息一起送，不要一個等一個。

把它們找到的東西融進一段平實的講解，從對方最關心的地方講起，對方追問時再往深裡說。講課時可以自由改寫，只有一個例外：保持 `why-code-work` 的置信度措辭不動（它的留有餘地是發現的問題，不是文風）。

1. 先定下對方讀完該弄懂的少數幾件事。依據他們為什麼問（正要改它、在審查它、在除錯它、剛接觸它）以及他們已經知道什麼來選，這兩點都從對話裡讀出來，不要靠提問去套。他們明顯已經知道的直接跳過。把深度放在他們提問的地方。

2. 讓 `how-code-work` 和 `why-code-work` 去幹活，不要自己重做一遍。自己先讀程式碼找準方向，然後跑 `how-code-work` 看它怎麼運作、跑 `why-code-work` 看它為什麼這樣。兩者一起跑，合併結果。規模要和問題匹配。整個子系統兩個都跑，一個小改動也許跑一個就夠了。預設讓 `why-code-work` 保持窄範圍，因為它的完整掃描很慢。把收窄寫進請求本身（一個限定範圍的問題，git 加一兩個原始檔），這樣它會按自己的約定記錄跳過的類別；只有當「原因」本身就是重點時，才把範圍放寬。

3. 先給一個平實的定義。給這東西命名，用通俗的話說清它是什麼，就像一個資深工程師脫口而出的那樣；如果它有常用叫法，就用常用叫法。然後把它和你面前的具體情況掛上（「在 X 裡，我們用它來……」），再由此鋪開：它怎麼運作、更深層的原因、邊界情況。每一部分都要把概念講到讓人開竅：它解決什麼問題，以及它到底怎麼運作。當「跟著對方做一遍」最能講透時，就走一遍他們會經歷的過程（開啟一個很長的對話、往上滾）。羅列函式和常量是 reference，不是講課。不要列印框架標籤（「要記住的那一個想法」「帶走的重點」「關鍵洞察」「本質上」「TL;DR」）。先給最小的完整答案，一兩句話，不要一上來就一大段，然後停下。對方追問時再加層次。絕不要寫成一堵文字牆。

4. 保持像對話，別變成講課或表演。主動問要不要往深講或繼續往下，跟著對方的節奏走。不要出題。不要搞節奏表演。不要列印「停一下」，不要讓他們複述，不要宣佈「這句要記住」，也不要標出哪部分重要或難（「這裡值得慢下來」「這比較繞」「這裡開始有意思了」）。直接說。該停頓的地方就停下，讓對方回應。一次跑完、沒有真人在場時，乾淨利落地交付，把「要不要往深講」的邀請放在結尾。

5. 要展示，不要只講述，而且要一張圖一張圖地把畫面搭起來。當開啟 diff、程式碼或偵錯程式是最快講透的辦法時，就開啟它們。畫面比文字更快講明白時就畫圖。只要涉及三個或更多的活動部件，就不要用一張圖一次畫全。改成畫一小串圖：每張都在上一張基礎上重畫，只加一個部件，讓讀者看著系統一點點組裝起來。一張一次性畫全的圖，尤其是留到最後才給的那張，是 reference，不是講課。具體說，要講一條 A 到 B 再到 C 的流程，就畫三遍。先畫 A 到 B。然後重畫，加上 C。再重畫，加上回路那條邊或下一塊。媒介要配得上要講的點，兩種媒介都有幫助時就用兩種。mermaid 圖適合標籤本身承載含義的流程或結構。要講的是空間關係時，比如佈局、重疊、滾動位置，或前後對比，若環境有影象生成工具，就用它畫成白板上馬克筆的風格，配幾個短標籤；影象模型處理長文字會出錯。要把那張圖畫出來，不要只滿足於用文字描述。沒有影象生成工具就退回 mermaid 或 ASCII。層層搭建的規則對生成的圖片同樣適用。單個簡單的點不需要配圖。

每一次回覆都要套用 **unslop** 的規則（`~/.agents/skills/unslop/SKILL.md`；它也是使用者顯式觸發的 skill，直接讀檔套用）。用平實的口語中文寫，就像跟同事解釋那樣。要緊湊，不是簡短。砍掉廢話和模稜兩可的措辭，留住讓人開竅的那部分。直接講具體的機制，不要用比喻、框架，或預告接下來要講什麼。這是目標密度：「虛擬化分兩部分跑，一部分管渲染，一部分管從磁碟載入。一項滾出緩衝區之後，它的 DOM 節點和記憶體裡的資料一起被清掉。」不用破折號。多用句號，少用逗號。每句話最多一兩個逗號。從句堆起來就拆成幾句。每個概念只給一個名字並一直用。避免映象句（「有 A 沒有 B，或有 B 沒有 A」）和收尾的金句（「其餘自然如此」「全都由此推出」）。這些步驟裡的話是對你的指示，不是要列印出來的標籤。不要把結構照搬成標題或套話。

**Reply:** 講解本身，絕不是關於你做了什麼或交付了什麼的報告。先講要點，再平實地講清它是什麼、怎麼運作、為什麼這樣，以及值得用 `how-code-work` 或 `why-code-work` 繼續追的線索。
