# 改寫範例

所有範例都是自造的。每個範例後面標出用到的規則編號。

## 1. 概念解釋

**改寫前**

> 值得留意的是，雜湊表之所以能夠達到平均常數時間的查找，很大程度上是因為它透過雜湊函式把鍵對應到陣列中的某個位置，不過當多個鍵被對應到同一位置的時候，就會產生所謂的碰撞，而碰撞的處理方式會對效能造成不小的影響。

**改寫後**

> 雜湊表查找一個鍵，平均只需要常數時間。原因是：雜湊函式把每個鍵算成一個陣列索引，程式直接去這個索引取值。
>
> 兩個不同的鍵可能算出同一個索引。這種情況叫「碰撞」。雜湊表處理碰撞的方法，對效能影響很大。

用到：13（刪「值得留意的是」）、5（拆句）、6（寫清主語）、1（給「碰撞」下定義）、14（保留「平均」「很大」）。

## 2. 操作步驟

**改寫前**

> 在開始之前，您需要先確認已經安裝了 Node.js，之後可以透過在終端機中執行 npm install 來安裝相依套件，安裝完成以後再執行 npm run dev，如果連接埠被佔用的話可以在 .env 檔案裡面修改 PORT。

**改寫後**

> 前提：本機已安裝 Node.js。
>
> 1. 在終端機執行 `npm install`，安裝相依套件。
> 2. 執行 `npm run dev`。
> 3. 如果提示連接埠被佔用，開啟 `.env` 檔案，修改 `PORT` 的值。

用到：9（編號、動詞開頭、不寫「您」）、3（「進行相依套件的安裝」→「安裝相依套件」）、8（條件放前面）、15（指令原樣保留）。

## 3. 解釋 agent 的產出

**改寫前**

> 我已經對整個程式碼庫進行了全面的梳理，並針對相關問題做了一些必要的調整，現在登入流程應該已經能夠比較穩定地工作了，不過可能還需要你這邊再驗證一下邊界情況。

**改寫後**

> 我改了 2 個檔案：
>
> - `auth/session.ts`：權杖過期時，先更新權杖，再重試請求。之前直接報錯。
> - `auth/login.ts`：密碼為空時，前端直接提示，不再送出請求。
>
> 我跑了現有的登入測試，全部通過。我沒有測這兩種情況，需要你確認：
>
> - 更新權杖也過期時，使用者是否被帶回登入頁。
> - 網路斷線時，重試會不會無限迴圈。

用到：2（「全面梳理」「必要的調整」換成具體動作）、12（並列內容用列表）、14（保留「需要驗證」這個限定，並寫清驗證什麼）。

注意：範例 3 的改寫需要原始資訊（改了哪些檔案）。原文沒有這些資訊時，不要編造。只寫「原文沒有說明改了哪些檔案」，並向對方要。

## 4. 不刪內容

**改寫前**

> 該方法在大多數情況下效果不錯，但對於樣本量較小（例如少於 30 個）且分布明顯偏斜的資料，結果可能不太可靠。

**錯誤改寫（刪了限定）**

> 該方法效果不錯。小樣本資料不適用。

**正確改寫**

> 這個方法在大多數情況下效果好。
>
> 有一種情況例外：樣本少於 30 個，並且分布明顯偏斜。這時結果可能不可靠。

用到：14（保留「大多數」「可能」「並且」這兩個條件同時成立）、5（拆句）、7（「不太可靠」→「可能不可靠」，少一層否定修飾）。

## 5. 套疊的修飾語

**改寫前**

> 負責讀取 `config.yaml`、把環境變數覆蓋到設定值上、並在缺少必填欄位時直接結束程式的那個初始化函式，在 `NODE_ENV` 為 `test` 時會跳過檔案讀取。

**改寫後**

> 有一個初始化函式負責三件事：
>
> 1. 讀取 `config.yaml`。
> 2. 用環境變數覆蓋設定值。
> 3. 缺少必填欄位時，結束程式。
>
> `NODE_ENV` 為 `test` 時，它跳過檔案讀取。

用到：5（拆套疊修飾語，逐句補主詞）、12（3 項並列改列表）、8（條件放前面）、15（`config.yaml`、`NODE_ENV`、`test` 原樣保留）。

## 6. 成語與文言虛詞

**改寫前**

> 這版快取的效益差強人意，命中率的提升幅度不無疑問，若日後流量持續成長，效能瓶頸恐有再現之虞，屆時應予重新評估。

**改寫後**

> 這版快取的效果勉強可以。命中率提升多少，還不確定。
>
> 如果流量繼續成長，效能瓶頸可能再出現。那時要重新評估。

用到：2（「差強人意」→「勉強可以」，不用成語）、3（「不無疑問」→「還不確定」；「恐有……之虞」→「可能……」；「應予重新評估」→「要重新評估」）、5（拆句）、14（保留「可能」這層不確定）。
